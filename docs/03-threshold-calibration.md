# 03 门限定标：尺子从哪里来

> 回答的问题：**用什么尺子判定 A2/A3？基线如何定标而不陷入循环论证？**
> 实现：`bench/baseline.py`（分桶、Phase 0、门限解析）、
> `bench/config.py`（`slo.*` 字段与校验）、`bench/report.py::_render_baseline_section`。

## 3.1 问题的提出

01 章把"成功"拆成 A2（达标）与 A3（不达标），但"达标"需要一个尺子：
TTFT 和 TPOT 各自超过多少算不达标？这个尺子（判定门限）从哪来，
是整套指标体系里最容易出错的一环——**尺子若随被测系统一起变化，
测量就失去意义**。

本章记录三个决策：SLA 目标不动态化；SLO 门限可以换尺子，
但绝不能用本次运行的分位数定标；尺子按长度分桶。

## 3.2 决策一：SLA 不动态化

`analysis.sla_target`（默认 0.999，3 个 9）是**固定配置值**，
不随任何测量结果变化。

理由：SLA 是**业务契约**。契约的意义在于先于测量确定——
"我们承诺 99.9% 可用"，然后拿服务去对账。如果目标可以随表现浮动，
就会出现"今年实际 99.5%，所以把目标改成 99.5%"的操作：
指标永远达标，验收永远通过，契约名存实亡。

同理，本工具也不提供"根据当次运行结果自动调整 SLA 目标"的路径。
目标只能由人显式修改配置，且修改本身应当是一次业务决策。

## 3.3 决策二：SLO 门限可自适应，但禁止循环定标

SLO 门限（TTFT/TPOT 目标值）的情况不同：不同推理引擎、不同模型规模、
不同硬件下的"合理时延"差别巨大——同一个 2 秒 TTFT 门限，
对 7B 模型可能绰绰有余，对 70B 长上下文模型可能永远达不到。
固定门限在跨引擎场景下要么过松（永远达标）要么过严（永远不达标），
失去分辨力。因此门限**需要能换尺子**。

但有一条绝对不能碰的红线：**绝不能用本次运行观测到的分位数定标**，
尤其是高压段的分位数。

### 3.3.1 循环论证分析

假设门限定义为"本次运行 TPOT p99 的 1.2 倍"，会发生什么：

```
高压级 → TPOT p99 被排队推高 → 门限随同步抬高
       → 大部分请求"达标" → SLO ≈ 目标值 → 指标永远合格
```

门限与压力同步抬升，SLO 恒约等于目标值——
**指标永真、无法验收**。更糟的是，它同时摧毁了两个功能：
压测失去"定位拐点"的能力（每级都"达标"），
运行间也失去可比性（尺子每次都不同）。

第二层问题更深：**用病态定义正常**。高压段的分位数本身就是
排队污染的结果——它度量的是"系统在过载时有多慢"，
而不是"多慢算不可接受"。拿被污染的量当基准，
等于把病症当成健康标准。

### 3.3.2 合法的尺子：与压力解耦的基线

正确做法是把尺子的来源移到**压力之外**：
Phase 0 用低到不触发排队/拒绝的并发，测量一段"无压力时延"，
以其分位数 × 显式系数作为门限：

```
门限 = Phase 0 基线 p99 × 系数（ttft_factor / tpot_factor，显式配置，≥ 1.0）
```

这个构造满足三个性质：

- **与压力解耦**：基线测于低压阶段，同一把尺子贯穿整个 ramp，
  跨级可比——SLO 随并发下降是真实的劣化，不是尺子在动；
- **可复现、可审计**：系数是配置值，基线分位数落库
  （`baseline` 表），门限 = 基线 × 系数，任何人都能重算；
- **跨引擎自适应**：换引擎/模型只需重测基线，整条曲线自动平移，
  不需要人工重设门限——这正是"可换尺子"诉求的正当实现。

### 3.3.3 两种模式的分工

| 模式 | 门限来源 | 性质 | 适用场景 |
| --- | --- | --- | --- |
| `absolute` | 固定配置值 `ttft_target_s` / `tpot_target_ms` | 业务契约口径，跨次运行可比 | **验收**（对外承诺、回归对比） |
| `baseline_relative` | 基线 p99 × 系数，按桶生效 | 自动适配引擎/模型规模 | **跨引擎适配、容量趋势观测** |

两种模式都不修改 SLA 目标，区别只在"用什么尺子量 A2/A3"。
注意 `baseline_relative` 的横向对比边界：**该口径下"达标"只对
当次基线有意义**。跨引擎/跨模型比较时应改用 absolute 口径，
或只对比报告中与门限无关的**质量退化率**（见 3.6）与原始分位数。
报告中会固定提示这一点。

## 3.4 Phase 0 基线剖析：设计要点

Phase 0 在正式 ramp 之前执行（`load.baseline_enabled`），
并发为 `baseline_concurrency`（必须低到不触发排队/拒绝），
持续 `baseline_duration_s`。设计要点：

1. **只统计分位数与失败数，不对 A2/A3 判定**。
   基线是尺子的来源，再拿它判达标会形成循环
   （"用尺子量尺子自己"）。`compute_baseline` 只输出分位数、
   样本数、失败数。
2. **样本不足的桶显式回退**。桶内成功样本 < `baseline_min_samples`
   时，其 p99 置信度不足，门限**回退为 absolute 配置值**，
   并在日志与报告中标注"（回退）"。绝不静默使用一个
   不可信的分位数——不可信的统计量比没有统计量更危险。
   基线阶段用独立的（通常更小的）样本量门限：按权重
   `[0.2, 0.5, 0.3]` 反推，最短桶要 30 个样本共需 150 个总样本，
   若与压力级共用 60 的门限则共需 300 个，多数部署的时限内
   补不齐——那会让 baseline_relative 在默认配置下永远失效。
3. **基线被污染要喊出来**。基线阶段出现任何失败请求
   （`total_a1 > 0`）说明"低压"并不低压，基线含排队，
   p99 虚高、门限虚松。工具会在报告中提示降低基线并发或
   排查可用性。
4. **可单独运行**。`--baseline-only` 只跑 Phase 0 并打印各桶
   分位数与生效门限：更换推理引擎/模型后，先确认尺子符合预期，
   再跑完整压测。
5. **每次运行重测，不复用旧基线**。避免基线随服务漂移
   （扩容、升级后基线已变而门限未变）。
6. **实际时长如实记录**。为补齐各桶样本量，基线可能被自适应延长
   （判据见 02.5.2）；`duration_s` 记配置值、`duration_actual_s`
   记实际值，报告同时展示两者，避免"配置 30s"与"实际跑了 3 分钟"
   对不上。延长结束仍不足时给出量化提示（还差多少样本、约需多少秒、
   建议并发），而不是让用户盲目增大时长。

## 3.5 长度分桶：尺子为什么要分档

### 3.5.1 问题：全局单门限把"长度差异"混进"排队劣化"

TTFT 与 prompt 长度强相关——prefill 计算量随上下文近似线性增长。
一条 8K prompt 的请求，TTFT 天然是一条 512 prompt 的十几倍。
若全局用同一个 TTFT 门限，只有两种结局：

- 门限按短 prompt 定：长 prompt 请求**天然**落入 A3，
  与排队无关——A3 被长度差异污染；
- 门限按长 prompt 定：短 prompt 的排队劣化被掩盖——
  门限失去了对短请求的分辨力。

两种结局下，"A3 增长"都无法回答"劣化是排队还是长度"。

### 3.5.2 分桶方案

`requests.length_buckets` 把请求按 prompt token 数分桶，
每个桶有独立门限：

```
length_buckets = [1024, 4096]
→ 桶 0：≤1024    桶 1：1025-4096    桶 2：>4096（无上界尾桶）
```

分桶后 A3 归因升级为二维：**超标侧**（TTFT/TPOT/双超标，
见 01.4）× **长度桶**。报告同时给出两个诊断：

- **A3 按桶拆分表**（桶内 A3 数 / 桶内总样本数，按桶×并发；
  分母含 A1，与分级表 SLA/SLO 分母一致）：
  若 A3 集中在长 prompt 桶而短桶仍全 A2，劣化源于 prefill 侧
  （长上下文计算量）；若各桶同步劣化，则是全局排队或准入问题。
- **质量退化率表**（见 3.6）：同一问题的量化版。

### 3.5.3 桶宽的设计约束

- 桶数 = 上界个数 + 1，尾桶无上界（兜住超长请求，避免数据丢失）。
- 每个桶必须有**足量样本**才有统计意义：桶数不是越多越好，
  样本量被桶数摊薄后，每个桶的 p99 都不可信。
   级样本量用 `min_samples_per_stage`，桶样本量用
   `baseline_min_samples`（更小，因为按权重反推的总量需求更大）。
- 桶边界应与生产流量分布匹配；`max_context_tokens` 只是能力上限，
  显式配置永远优先（见 3.7）。

## 3.6 质量退化率：与门限无关的诊断量

分桶门限解决了"尺子按长度分档"，但还有一个残留问题：
`baseline_relative` 口径下，各次运行的尺子不同，**跨次/跨引擎的
曲线不可比**。为此报告提供**质量退化率**：

```
退化率(并发 c, 桶 b) = 该级该桶的 p99 ÷ Phase 0 基线该桶的 p99
```

这个量**与门限完全无关**——只依赖原始分位数之比，
因此跨引擎、跨模型、跨次运行可比：

- 退化率 ≈ 1：该长度桶尚未受压力影响；
- 某桶退化率显著高于其他桶：劣化集中在对应长度区间
  （长 prompt → prefill 容量；短 prompt → 准入排队）；
- 全桶同步抬升：全局排队/准入问题。

退化率把"哪里在劣化"从定性读表升级为定量对比，
是 baseline_relative 口径下做横向比较的正确工具
（而不是比较"是否达标"）。

## 3.7 长度参数与 max_context_tokens：能力上限不是流量画像

`prompt_token_targets`（压测请求的长度分布）有一个看似自然的
默认值来源：模型的上下文上限。但**能力上限不等于流量画像**：

- 128K 上下文模型，若生产流量 90% 在 2K token 以内，
  按上限推导会大量打出 32K+ 长 prompt——TTFT 特性完全不同，
  容量拐点定位错误；
- 反之 8K 模型写死 32K 的默认值，直接触发校验失败。

因此工具的规则是：**显式配置永远优先；留空时才按
`max_context_tokens` 推导**（`[ctx/64, ctx/16, ctx/4]`，
权重 [0.2, 0.5, 0.3]，即"短多长少"的默认流量假设）。
推导来源记录在 `Config.derived_lengths`，启动横幅与报告
"请求特征覆盖"一节都会标注，**可审计**——
读者永远知道哪些数字是配置的、哪些是推导的。

## 3.9 本章小结

- SLA 是业务契约，恒为固定配置值，不动态化。
- SLO 门限可以换尺子（跨引擎适配），但**绝不能用本次运行的
  分位数定标**——那会形成循环论证：门限随压力抬升，
  SLO 恒等于目标，指标永真；且高压分位数已被排队污染。
- 合法的尺子来自与压力解耦的 Phase 0 基线：基线 p99 × 显式系数，
  只统计、不判定，样本不足显式回退，被污染会喊出来。
- 尺子按 prompt 长度分桶，把"长度差异"从"排队劣化"中分离；
  质量退化率提供与门限无关的跨引擎可比诊断。
- 长度分布应镜像生产流量画像；`max_context_tokens` 只在
  未显式配置时作为推导基准，且推导可审计。
