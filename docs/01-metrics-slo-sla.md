# 01 指标体系：A1/A2/A3、SLA 与 SLO

> 回答的问题：**用什么量"服务好不好"？为什么是三个分类、两个口径？**
> 实现：`bench/metrics.py`（分类与聚合）、`bench/client.py`（失败类型）、
> `bench/report.py::build_conclusions`（结论口径）。

## 1.1 为什么"成功率"不够用

传统 Web 服务的成功率假设是：**失败是二元的、快速的**。一次失败的 API 调用在
几十毫秒内返回错误码，用户立刻知道并可以重试；而成功请求的响应时间在秒级以内，
"慢一点"不影响可用性判断。

大模型推理服务两条都不成立：

- **失败是慢的**。一次超时的请求可能已经消耗了数分钟 GPU 时间；
  空输出、流中断这类"半失败"只在消费完整条流之后才能发现。
- **成功也可以是坏的**。排队 90 秒后完整输出的请求，从 HTTP 语义看
  "成功"，从用户视角看与失败没有区别——用户已经离开。

因此单一成功率会把两类完全不同的现象混为一个数字：系统是"崩了"还是"慢了"。
压测要做容量规划，必须能分开回答这两个问题。本工具的答案是
**请求三分类 + 两个派生口径**。

## 1.2 请求三分类

| 类别 | 定义 | 代码 |
| --- | --- | --- |
| **A1 失败** | HTTP 错误（含 Router 过载拒绝 429/503）、连接失败/重置、整体超时、流内错误、流异常结束、成功但 0 输出 token、协议解析失败 | `client.py` 的 `KIND_*` 常量，共 10 种子类型 |
| **A2 达标** | 成功，且 TTFT ≤ 门限 且 TPOT ≤ 门限 | `metrics.py::classify` |
| **A3 不达标** | 成功，但 TTFT 或 TPOT 超出门限（"慢但成功"） | 同上 |

派生指标（N = 总请求数，**不含被放弃的 aborted**，见 04 章）：

```
SLA（可用性） = (A2 + A3) / N      "请求有没有被正确服务"
SLO（质量）   =  A2      / N       "请求是否被快速服务"
```

设计要点：

- **A3 是压测的核心产出**。A1 反映硬故障，通常有明确的工程修复路径；
  A3 反映容量不足，它是随并发增长而连续劣化的量——**定位 A3 出现的位置，
  就是定位容量边界**。A1 是台阶，A3 是斜坡。
- **A1 必须细分错误类型**。`rejected`（Router 过载拒绝）与 `timeout`
  （配置不当）指向完全不同的行动：前者要扩容或调准入，后者要改 `timeout_s`。
  报告第六节按类型构成给出 Top3。
- **A1 内部再分两个归因家族**（`bench/metrics.py: split_fail_kinds`，不影响
  分类、只影响"过载长什么样"的解读）：**拒绝族**（`rejected`/`http_4xx`/
  `http_5xx`/`stream_error`）= 服务端明确回绝；**超时族**（`timeout`/
  `connect_timeout`）= 服务不拒绝但请求在客户端预算内未完成。Router 配
  **无限队列**（无 429/529）时，过载的唯一投影就是超时族——分类上仍是
  A1、仍拉低 SLA、仍触发硬水位，但治理动作完全不同（见 [05](05-watermark.md)
  2.1：先给队列设上限，而不是调高客户端超时）。
- **A1 中的 rejected 依赖 Router 行为**：过载必须能被客户端观测到
  （429/503 或报文含 overload/queue full）。若部署的 Router 用其他信号
  表达过载，需在 `client.py` 补充识别，否则过载会被误记为"慢"（A3）而非
  "拒绝"（A1），容量结论会偏乐观。

## 1.3 两个口径必须分开看

SLA 与 SLO 的差别在"算不慢 A3"：

- **SLA = 接得住**。请求最终拿到了正确、完整的响应，无论多久。
  这是传统的可用性契约，99.9%（3 个 9）是常见目标。
- **SLO = 接得好**。请求不仅成功，而且在用户可感知的时延预算内完成。
  这是质量契约。

**为什么不能只看 SLA——排队型过载陷阱**：
推理服务在过载时有两种截然不同的策略，压测中都会真实出现：

| 过载策略 | 观测表现 | SLA | SLO |
| --- | --- | --- | --- |
| 排队消化（Router 缓冲） | A1=0，TTFT/TPOT 持续抬升，A3 增多 | 维持 100% | 持续劣化至归零 |
| 拒绝保护（队列上限） | A1 增多（rejected），A3 相对稳定 | 断崖下跌 | 相对保持 |
| 无限队列（无上限排队） | A1 增多（timeout，全程无 429/529），A3 相对稳定 | 断崖下跌（超时计失败） | 相对保持 |

排队型过载下，**SLA 永远"达标"，但系统已经没有任何实用价值**——
每个请求都"成功"，只是都要等几分钟。此时若按 SLA 容量定生产并发，
等于把系统运行在用户不可用的区间。这正是本工具把
**质量容量**（SLA 与 SLO 同时达标的最高并发）作为生产建议唯一基准的原因：
SLA 容量仅作为 3 个 9 可用性参考**单独陈述**，并在该点 SLO 不达标时
明确标注"此容量无实际服务质量意义"。

> 这对应 SRE 实践中"可用性目标"与"性能/体验目标"分离的原则：
> 一个只保证"不丢请求"的系统，可以是完全不可用的系统。

## 1.4 TTFT 与 TPOT：时延结构对应 PD 分离的两个阶段

流式采集三个时间量（口径见 04.5，全部基于单调时钟）：

```
TTFT ──────────────── 流结束
│← 排队 + prefill →│←───── decode ─────→│
  首 token 时间          每 token 平均间隔（TPOT）
```

- **TTFT（Time To First Token）= 客户端视角的首 token 等待**。
  计时从建连之前开始（`client.py` 的 `t_start`），因此包含 TCP/TLS 建连、
  请求写出、网络、Router 排队、调度、prefill 计算。选这个口径是因为
  **用户感知到的就是这段等待**；建连开销单独记录为 `connect_ms`
  （建连+写出+等响应头），报告中给出各级 p50/p99，跨机房/TLS 部署下
  占比可观时应予扣除或把客户端部署到靠近服务的网络位置。
  PD 分离架构中 prefill 计算量随 prompt 长度近似线性增长，
  因此 TTFT 与 prompt 长度强相关。
- **TPOT（Time Per Output Token）= 首 token → 末 token 的平均每 token 间隔**。
  反映 decode 侧稳态吞吐，由 batch 调度、KV cache 带宽决定，
  与输出长度关系较弱（若不考虑 KV 随上下文增长导致的减速）。

**为什么这两个量分开看**：它们的劣化指向不同的优化动作，
这是 A3 归因的理论基础——

| 劣化侧 | 物理原因 | 优化方向 |
| --- | --- | --- |
| TTFT 为主 | 排队、prefill 容量不足、准入并发受限 | 扩容 PD 副本、提高 Router 准入/调度并发、排查 prefill 热点 |
| TPOT 为主 | decode 吞吐不足（batch、KV 带宽） | batch 调度优化、增大 KV 复用、扩容 decode 副本 |

归因判据见 `report.py::build_recommendations`：统计"仅 TTFT 超标"、
"仅 TPOT 超标"、"双超标"三类计数；双超标同时计入两侧——
排队场景下 TTFT 先爆，TPOT 往往是被长队列连带拖垮的。

**短输出的 TPOT 免检**：`min_completion_tokens`（默认 2）以下的请求，
TPOT 分母过小、统计噪声极大，不参与 TPOT 判定（`classify` 中
`tpot_ok = True`）。否则极短输出会把随机噪声计入 A3。

## 1.5 边界情形的处理

| 情形 | 处理 | 理由 |
| --- | --- | --- |
| 成功但 0 输出 token | 判 A1（`empty_completion`） | 对用户无任何信息量，等同失败 |
| 流异常结束且无内容 | 判 A1（`incomplete`） | 半截流不可用 |
| 本级结束仍在途 | 记 `aborted`，**不计入 A1/A2/A3** | 无法判定成败；计入会同时污染两个口径（见 04.1）。`sent_at` 记录真实发出时刻，供审计 |
| 预热段请求 | 落库但统计时排除 | 冷启动不反映稳态（见 04.2） |
| 无 usage 字段 | `chars_per_token` 估算 token 数，落 `token_source=estimated` | 估算仅用于分桶近似，报告中给出偏差告警（见 04.7） |
| 正式压力级的每条请求 | 落库时即回填 `latency_class`（A1/A2/A3） | requests 表可直接按类别检索，无需重算（见 03 章门限） |

## 1.7 本章小结

- 成功率在分钟级时延的服务上失效，因为它把"崩了"和"慢了"混为一谈。
- A1/A2/A3 三分类把"失败"与"慢但成功"分开；SLA/SLO 两个口径分别回答
  "接得住"与"接得好"。
- 排队型过载会制造"SLA 100% 而 SLO 归零"的假象，因此生产并发建议
  **只认质量容量**（双达标），SLA 容量单独陈述。
- TTFT 与 TPOT 的劣化指向不同的物理瓶颈，这是后续所有 A3 归因的基础。
