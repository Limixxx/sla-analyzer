# 02 容量模型：PD 分离与递增并发压力

> 回答的问题：**系统什么时候"接不住"？递增并发如何试探出容量边界？**
> 实现：`bench/runner.py`（压力编排）、`bench/metrics.py::find_capacity`
> （容量提炼）、`bench/store.py`（落库）。

## 2.1 PD 分离为什么改变了容量问题的形状

标准推理部署把 prefill 与 decode 放在同一组实例上交替执行。PD 分离
（Prefill/Decode disaggregation）把两者拆到独立的实例组：

```
                 ┌─ Prefill 实例组（计算密集）─┐
请求 → Router ──┤                            ├→ KV cache 传输 ─┐
                 └─ Decode  实例组（显存/带宽密集）┘              ↓
                                                        逐 token 流式返回
```

- **prefill 阶段**是计算密集的：一次处理整个 prompt，计算量随 prompt 长度
  近似线性增长。它决定 TTFT。
- **decode 阶段**是显存与带宽密集的：每步只生成一个 token，需要读取
  全部 KV cache。它决定 TPOT。
- 分离的收益是两侧可以**独立扩缩**、互不干扰；代价是 KV cache 需要
  跨实例传输（bootstrap 通道），且 Router 必须做 PD 匹配。

对容量压测的含义是：**系统有两个可饱和的资源平面**，且过载信号
分别体现在 TTFT（prefill/排队侧）与 TPOT（decode 侧）上。
这正是 01 章两个时延口径的架构根源，也是 03 章按长度分桶的原因——
不同长度区间的请求消耗 prefill 资源的速率不同。

## 2.2 过载的两阶段：先排队，后拒绝

后端资源饱和后，系统对外表现取决于 Router/调度层的缓冲策略，
压测中会依次观察到两个阶段：

```
A1 ┤                                        ╭─
   │                                   ╭────╯   ← 阶段二：拒绝
   │                              ╭────╯        队列打满，返回 429/503
   ├───────────────────────╭─────╯
   │                  ╭────╯                     ← 阶段一：排队
A3 ┤            ╭─────╯                          队列吸收压力，
   │       ╭────╯                                TTFT/TPOT 抬升，
   │  ╭────╯                                     A3 增多
   └──┴────┴─────┴─────┴─────┴─────┴─────► 并发
     拐点前   阶段一（排队）   阶段二（拒绝）
```

- **阶段一（排队）**：请求被缓冲等待，不失败但变慢。表现为 A3 增长、
  TTFT 与 TPOT 分位数抬升，A1 ≈ 0。SLA 维持，SLO 劣化。
- **阶段二（拒绝）**：队列到达上限，Router 主动返回过载错误
  （保护后端不被无限拖垮）。表现为 A1 中 `rejected` 增多，
  SLA 断崖下跌；而此时**在途请求的时延反而可能不再恶化**——
  拒绝本身起到了限流作用。

这个两阶段结构是排队论的宏观体现：利用率 ρ→1 时等待时间按
~1/(1-ρ) 发散，系统要么把压力转成排队时间，要么在缓冲上限处拒绝。
**压测的任务就是找到两个阶段的交界——容量拐点（knee）**，
并按 01 章的口径分别定位：首个 SLO 跌破点（`first_slo_breach`，
质量开始劣化）与首个 SLA 跌破点（`knee_concurrency`，可用性受损）。

## 2.3 为什么用"递增并发"而不是一步到顶

容量边界的定义本身就要求一条曲线：容量 = "满足目标的最大负载"，
而负载-指标关系是非线性的（见 2.2）。递增并发（ramp）逐级施压：

1. **低压级**提供无压力基线（Phase 0 还单独测一次，见 03 章），
   同时验证低压级别的质量，防止"从坏状态开始测"；
2. **中压级**捕捉排队起点：A3 从 0 开始出现的级别就是拐点区域；
3. **高压级**确认拒绝行为，并检验目标失败模式是排队还是拒绝。

一步到顶的直接压力只能回答"这个点行不行"，无法回答
"从多少开始不行"，也无法给出生产并发建议——生产运行需要知道
拐点在哪里，而不是只要一个过载点。

## 2.4 闭环（closed）与开环（open）

工具支持两种压力模型（`load.mode`）：

| 模式 | 机制 | 回答的问题 | 本工具的定位 |
| --- | --- | --- | --- |
| **闭环 closed** | 固定并发数，每个 worker 串行发请求直至本级结束 | "系统能同时服务好 N 个并发用户吗" | **默认，容量探测的标准方式** |
| 开环 open | 按固定 RPS 发送，不控制在途数 | "系统的吞吐上限在哪" | 辅助，用于观察 RPS 饱和点 |

闭环是容量压测的正确默认，因为：并发是用户行为的直接代理
（同时有多少人在用），而后端饱和会**自然体现在响应变慢上**——
排队使每个 worker 的循环周期变长，闭环系统自限流，A3 增长先于 A1。
若用开环以过高 RPS 冲击，会跳过排队阶段直接进入拒绝，
丢失"质量从多少开始劣化"的信息。

## 2.5 编排细节的方法论依据

### 2.5.1 预热段排除

每级分预热段与测量段（`warmup_s` / 测量段），预热数据落库
（`is_warmup=1`）但**不进入任何统计**。原因：换并发级后，
Router 的路由表、连接池、调度器的 batch 组合、GPU 上的
KV cache 布局都处于瞬态，前几秒的时延不代表稳态。

### 2.5.2 低压级别的自适应延长

闭环模式下，样本产出速率受 Little's law 约束：

```
在途请求数 N = 吞吐 X × 响应时间 R   ⇒   X = N / R
```

并发 1、单请求 E2E≈3.5s 时，60s 最多产出约 17 个样本——
远低于统计判定所需的样本量。若按固定时长收工，**低压优质级别
会因为样本不足被整体排除在容量判定之外**，恰好丢失最重要的参照点。

因此 `runner.py` 在测量段结束时检查：样本数 < `min_samples_per_stage`
且未达 `max_stage_duration_s` 上限时，以 30s 步长自动延长本级。
延长会在日志中显式提示，不是静默行为。

### 2.5.3 每级请求数上限

`max_requests_per_stage` 防止高压级样本爆炸：进入拒绝阶段后
单请求在毫秒级完成，不设上限一晚上能跑出千万级记录。

### 2.5.4 drain 窗口与在途请求

本级结束时仍在途的请求等待 `drain_timeout_s`，超时后取消并记为
`aborted`。drain 窗口必须大于最长合法 E2E，否则最慢的请求
（恰恰是 A3 的主要候选）会被系统性丢弃——这是存活者偏差，
详见 04.1。

## 2.6 连续前缀规则：容量怎么从曲线里提炼

`find_capacity` 从分级结果中提炼容量，核心规则是
**连续前缀**：按并发升序扫描，只有从低压到高压**每一级都达标**的
并发才认定为有效容量，遇到第一个样本充足且不达标的级别即停止。

```
SLO ┤ ████████████░░░░░░░░
    │ 达标前缀（有效容量）  ↓ 此后即使反弹也不认
    └──┴──┴──┴──┴──┴──┴──┴──► 并发
              ↑ 质量容量 = 最后一个达标级
```

为什么不用"所有达标级里的最大值"：单级统计量有抽样波动，
某个高压级可能偶然达标（如该级恰好多弹出短 prompt）。
把这种反弹计入容量会系统性高估。前缀规则只认"稳定达标区间"；
若更高处出现反弹，会在报告 notes 中提示"中间存在抖动，
建议复测确认"。

样本不足（< `min_samples_per_stage`）的级别**不进入前缀**，
但也不被丢弃：若样本充足的前缀为空，工具给出
**低置信度参考容量**（放宽样本量后的前缀结果），并在结论中
明确标注"低置信度，需延长低压级时长后复测"。
这防止低压优质级别因样本量被无声丢弃，也防止把
低置信结论包装成高置信建议。

三个容量口径分别陈述（01 章的口径在此落地）：

| 口径 | 定义 | 用途 |
| --- | --- | --- |
| 质量容量 | SLA ∧ SLO 双达标的最高连续前缀 | **生产并发建议的唯一基准** |
| 3 个 9 容量 | SLA 达标的最高连续前缀 | 可用性参考；该点 SLO 不达标时明确标注无质量意义 |
| SLO 容量 | SLO 达标的最高连续前缀 | 质量侧参考（通常 SLA 先破，此值 ≥ 质量容量） |

## 2.7 压测结论外推到生产的边界

压测是**受控实验**，结论外推需要流量画像匹配：

- **长度分布**：压测请求的 prompt/输出长度分布必须镜像生产
  （见 03.7 与配置注释）。对 128K 模型按上限打满 32K 长 prompt，
  测出的拐点与生产流量（90% 在 2K 内）毫无关系。
- **到达模式**：闭环测的是并发容量；若生产是突发流量，
  还需关注拒绝策略下的排队深度，必要时补开环 RPS 测试。
- **时变因素**：30 分钟长稳验证（报告建议）用于捕捉
  内存碎片、缓存衰减等随时间漂移的现象。

## 2.9 本章小结

- PD 分离把系统分成 prefill 与 decode 两个可饱和平面，分别对应
  TTFT 与 TPOT，容量问题因此有两个观测面。
- 过载表现为两阶段：先排队（A3 增长、SLA 维持），后拒绝
  （A1 增长、SLA 断崖）；压测的任务是定位两阶段的交界。
- 递增并发 + 闭环模式是容量探测的标准方法；预热排除、
  低压自适应延长、请求数上限、drain 窗口都是为了让每一级
  的统计量可信。
- 容量结论用连续前缀规则提炼，生产建议只认质量容量；
  样本不足显式降级为低置信度参考。
