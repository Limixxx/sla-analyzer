# 04 测量有效性：让数字不说谎

> 回答的问题：**测出来的数字为什么可信？偏差从哪来、怎么控？**
> 实现：`bench/stats.py`（分位数）、`bench/runner.py`（aborted/预热/延长）、
> `bench/prompts.py`（前缀/长度合成）、`bench/client.py`（时间口径）。

方法论前三篇定义"量什么、怎么压、用什么尺子"；本篇处理最后一个问题：
**测量过程本身会系统性地把结论带偏**。压测工具的可信度不取决于
代码能跑多快，而取决于这些偏差是否被识别和控制。
下表是威胁模型总览，后面逐条展开。

| # | 偏差 | 不控制的后果 | 控制手段 |
| --- | --- | --- | --- |
| B1 | 存活者偏差 | 最慢的请求被静默丢弃 → 时延与 A3 系统性低估 | `aborted` 单列，不进任何比率 |
| B2 | 冷启动偏差 | 前几秒瞬态污染稳态统计 | 预热段排除 |
| B3 | 样本不足 | 低压优质级别被丢弃或低置信结论被当高置信 | 自适应延长（按量/按桶）+ 显式降级标注 |
| B4 | 分位数口径混乱 | 门限随样本插入被"平均"拉偏，跨次不可比 | 最近秩定义 |
| B5 | 时钟口径不当 | 系统时钟抖动伪造时延 | 单调时钟 |
| B6 | 前缀缓存美化 | "热"路径 TTFT 虚低，拐点偏乐观 | 唯一前缀（可配置） |
| B7 | 长度估算失真 | 长度分布未按预期覆盖，分桶失效 | usage 优先 + 偏差告警 |
| B8 | 客户端视角局限 | 把服务端瓶颈误读为客户端观测 | 明确边界，联动服务端监控 |
| B9 | 时间戳口径失真 | 超时/放弃请求的时间戳取"发现时刻"，墙钟窗口被推晚 → RPS 低估 | 发出时刻在进入等待前一次性取样 |

## 4.1 B1 存活者偏差：最危险的偏差

本级结束时仍在途的请求，是最慢的请求——它们恰恰最可能属于 A3。
如果简单地"只统计已完成的请求"，这些样本被静默丢弃，
幸存下来的都是偏快的请求，后果是：

- 时延分位数（p99 尤其）系统性低估；
- A3 占比低估，SLO 虚高；
- 高压级的劣化被抹平，容量结论偏乐观。

这在统计上是典型的**截断数据**（truncation）问题：
观测条件（"在窗口内完成"）与观测值（"快"）相关，
样本不再代表总体。

工具的控制手段是**显式单列而非丢弃**：

- 超过 `drain_timeout_s` 仍在途的请求记为 `status=aborted`
  （`KIND_ABORTED`），落库、单独计数（`n_aborted`）；
- **不计入 SLA/SLO 分母，不进入任何分位数**——
  它们的成败确实无法判定，计入任一口径都是编造；
- 但**总量要可见**：日志与报告展示每级放弃数，
  占比偏高时提示"应增大 `load.drain_timeout_s`"；
  某级 `n_total=0` 时结论直接给出复测提示，
  而不是给一个基于空样本的荒谬容量；
- `sent_at` 记录**真实发出时刻**（`_issue` 在调用前取样），
  而不是取消时刻——否则时间戳说谎，审计与窗口统计都会被带偏
  （见 B9）。

配套约束：`drain_timeout_s` 必须大于最长合法 E2E。
分钟级请求下这是硬要求——否则每个慢请求都会被放弃，
B1 从"罕见边界"变成"系统性失真"。

> 这与生存分析中"删失数据必须显式建模"的原则同源：
> 不可观测的样本不能被当作不存在。

## 4.2 B2 冷启动偏差：预热段

每级切换并发后，系统处于瞬态：Router 更新路由、连接池重建、
调度器重新组合 batch、GPU 上 KV cache 布局迁移。
前几秒的时延包含这些一次性成本，不代表稳态。

控制手段：每级分预热段与测量段（`warmup_s`），预热数据落库
（`is_warmup=1`）但统计时排除（`stage_rows(include_warmup=False)`）。
保留落库是为了可审计——需要时可以复盘预热时长是否足够
（预热段放弃数单独统计，因为预热段被 drain 同样说明窗口不够）。

## 4.3 B3 样本量：结论的置信度从哪来

**3 个 9 的判定需要多少样本？** 比例类指标的不确定性按二项分布
估计，标准误 ~ sqrt(p(1-p)/n)：

| 目标 | 需要多少样本才能与邻近值区分 |
| --- | --- |
| 99.9% vs 99.5% | 每级 ≥ 1000 条 |
| 99.9% vs 99.0% | 每级 ≥ 数百条 |

闭环低压级别的样本产出受 E2E 限制（Little's law，见 02.5.2），
天然达不到大样本。工具的分层处理：

1. **尽力延长**：测量段样本不足时自动延长至 `max_stage_duration_s`
   （正式级按总量、基线阶段按最短长度桶，判据不同因为"够用"的定义
   不同，见 02.5.2 与 03.4）；
2. **分层置信度**：样本 ≥ `min_samples_per_stage` 的级别进入
   高置信度前缀；不足的级别不参与前缀，但进入**低置信度参考容量**
   并在结论中明确标注"低置信度，需复测确认"；
3. **显式提示**：报告在分级结果表下方列出样本不足的级别，
   在容量结论处说明其对结论的影响。

原则：**样本不足时降低结论的置信度，而不是编造一个数字**。
低置信度参考容量不是"退而求其次的答案"，而是"复测指引"。

## 4.4 B4 分位数口径：为什么是最近秩

分位数有两种常见定义：**插值法**（线性内插两个相邻次序统计量）
与**最近秩法**（第 q 分位数 = 排序后第 ceil(q×N) 小的值，不插值）。
工具选后者（`bench/stats.py::percentile`），理由：

- **门限来源需要稳定性**：分位数作为 baseline_relative 门限的
  来源时，不应因个别新样本插入而被"平均"拉偏。最近秩下，
  分位数只在新样本跨过秩边界时跳变，行为可预期；
- **可解释性**：p99 直接对应"最慢 1% 的边界样本"，
  现场复盘时能指出具体是哪条请求。

已知局限（必须知道）：样本量不足 100 时，最近秩 p99 就是样本最大值
（N=60 时 ceil(0.99×60)=60，即最大值）——小样本下 p99 极不稳定。
这正是基线阶段要求每桶 ≥ `baseline_min_samples`、
以及退化率表同时给出分位数原始值的原因——**分位数从来不是单独使用的**。

## 4.5 B5 时间口径：单调时钟与客户端视角

所有时延基于 `time.monotonic()`，不用墙钟。原因：NTP 校时、
闰秒调整会让系统时钟跳变，用墙钟测量区间可能得到负时延或
虚高时延。单调时钟保证区间测量不受系统时钟影响。

TTFT/E2E 的起算点在**建连之前**（`client.py` 的 `t_start`），
即客户端视角：用户从发起请求到看到首 token 的全部等待，
包含 TCP/TLS 建连与请求写出。选这个口径是因为它回答的是
"用户等了多久"；建连开销单独记录为 `connect_ms`，
报告在延迟分布一节给出各级 p50/p99——跨机房/TLS 部署下
该项可能占 TTFT 的相当比例，解读时需扣除，
或把压测客户端部署到靠近服务的网络位置。

TPOT = (末 token 时刻 − 首 token 时刻) / (输出 token 数 − 1)：
首尾差分除以间隔数，避免把 TTFT 算进每 token 成本。

## 4.5b B9 时间戳口径：发出时刻 vs 发现时刻

`sent_at`（墙钟）只用于吞吐窗口统计：RPS 的分母是
`max(sent_at + e2e) − min(sent_at)`。如果超时或被放弃的请求
把"发现问题的时刻"当作"发出时刻"记录下来，窗口的右端会被
推晚——单条 600s 超时能把整级 RPS 打到接近零，
而服务的真实吞吐完全正常。

控制手段：`sent_at` 在进入 `wait_for` **之前**一次性取样，
超时处理器复用该值重建结果（`client.py::execute_request`）；
`runner._issue` 同样在调用前取样，供 aborted 记录使用。

## 4.6 B6 前缀缓存：测"冷"还是测"热"

推理服务普遍有前缀缓存优化：相同前缀的 prompt 可复用 KV cache，
显著降低 TTFT。压测如果重复发送相同内容，测到的是缓存命中后的
"热"路径——TTFT 虚低、容量偏乐观，且完全不代表生产里
冷请求的体验。

工具默认 `unique_prefix=true`：每个请求附加唯一 nonce 前缀，
以少量 token 为代价换取无缓存干扰的测量。
若生产的关键路径确实依赖前缀缓存命中（如系统提示词固定的场景），
可关闭它以测量"热"路径——**但必须在报告里说明口径**，
两种口径的数字不可混用。

## 4.7 B7 长度估算：usage 优先 + 偏差告警

工具不依赖外部 tokenizer，用 `chars_per_token`（默认 3.5，
中英文混合估计）合成近似目标长度的 prompt。这会引入两层近似：

1. **合成近似**：字符数 → token 数的比例与真实 tokenizer 有偏差；
2. **分桶近似**：若请求的实际 prompt token 与计划值偏差大，
   分桶会错桶（长请求落进短桶，门限失真）。

控制手段：

- **真实值优先**：服务端 `usage` 字段的 `prompt_tokens` 优先用于
  分桶与统计，落库 `token_source=usage`；估算仅兜底
  （`token_source=estimated`）；
- **偏差告警**：报告"请求特征覆盖"一节对比"实测平均 prompt token"
  与"计划加权平均"，偏差超 15% 时给出校准建议
  （`chars_per_token / (1 + dev)`）并警告"长度分布未按预期覆盖"；
- **计划值落库**：`prompt_tokens_planned` 与 `prompt_tokens` 并列落库，
  复盘时可还原每次分桶依据。

## 4.8 B8 客户端视角的边界

本工具测量的是**客户端视角**的可用性与质量：用户等到了什么。
它不能回答服务端发生了什么——GPU 利用率、KV cache 占用、
队列深度、PD 匹配失败率需要从集群侧采集（Prometheus 等）。

两个视角的典型错位：客户端看到 TTFT 抬升（排队），
服务端的真相可能是 prefill 批次打满、KV 传输阻塞、或
Router 匹配等待。压测定位"用户体验从多少并发开始劣化"，
服务端监控回答"为什么"。**容量结论要落地，两侧必须对时联查**。

## 4.9 工程可靠性相关的测量纪律

- **超时配置**：`timeout_s` 必须大于最长合法请求时长（分钟级）。
  设小了会把慢请求误判为 `timeout`（A1）而非 A3——
   SLA 被污染，而问题的真相（慢）被掩盖成另一个问题（失败）。
   上线前用 `--probe` 实测最长请求。
- **压测机自身上限**：单进程闭环压测建议到数百并发；
  客户端自身 CPU/连接数成为瓶颈时，测到的是压测机的极限
  而非服务的极限。更高压力用多机运行、各自写独立 db 后
  合并 `requests` 表分析。
- **配置 fail-fast**：`validate()` 在启动时拦截一切非法配置
  （时长为负、权重长度不一致、超限请求、桶非递增、
  系数 < 1 等）。跑几十分钟后才发现配置错误是最贵的失败。

## 4.11 本章小结

- 测量偏差不会被"多跑几次"自动消除，只能被显式识别和控制。
- 最危险的是存活者偏差（B1）：最慢的请求最有信息量，
  工具把它们单列为 aborted——不计入比率，但必须可见。
- 冷启动、样本不足、分位数口径、时钟、前缀缓存、长度估算、
  时间戳口径各有对应的控制手段，共同原则是：**要么控制，要么标注，
  绝不静默**。
- 客户端视角有边界：容量结论落地时必须联动服务端监控。
